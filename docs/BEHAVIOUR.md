# Behaviour

What gherkin-glass-action promises, in terms a test can observe. Each section is written when its issue is agreed, before it is built, and every rule in it names the test that checks it ([AGENTS.md](../AGENTS.md), "Rules", rule 2). What `ghg` itself does is promised by gherkin-glass's [docs/BEHAVIOUR.md](https://github.com/marlon-sousa/gherkin-glass/blob/main/docs/BEHAVIOUR.md), whose rules this document names as "gherkin-glass's rule N".

## Status

Agreed so far:

- Every section below up to "Releases", issue [#1](https://github.com/marlon-sousa/gherkin-glass-action/issues/1), which carries over gherkin-glass's rules 169 to 177, of its own action, as that issue's decisions change them.
- "Outputs", "Publishing", "The publish action" and "The preview action", issue [#9](https://github.com/marlon-sousa/gherkin-glass-action/issues/9).
- The pairing with ghg 1.1.0, which adds `keep-in-output`, Windows on ARM64, the report the action reads, and what it does when there is nothing to build, issue [#12](https://github.com/marlon-sousa/gherkin-glass-action/issues/12).
- The scenarios that check the rules by running whole workflows, issue [#16](https://github.com/marlon-sousa/gherkin-glass-action/issues/16).
- A preview's title that names its pull request, rule 30, issue [#19](https://github.com/marlon-sousa/gherkin-glass-action/issues/19).

## The action

A step of a GitHub Actions workflow that says `uses: marlon-sousa/gherkin-glass-action@v1` installs `ghg` on the runner and, when asked, builds a site with it. The action is a JavaScript action, `using: node24` in `action.yml`, which the runner runs on the Node it carries itself, so it needs no Node on the job's `PATH`, and runs alike on GitHub's own runners and on self-hosted ones.

When the action stops, it says why in one sentence, which the workflow's log shows as an error, and the step fails. Every input is checked before anything is listed or downloaded. An error the action does not foresee, which is a bug, stops it with `The action failed unexpectedly: <error>`. Checked by `test/services/running_action.test.ts` and `test/services/reading_inputs.test.ts`.

The tests named below are under `test/`, run by `npm test`, unless they are jobs of `.github/workflows/action.yml`, which run the action itself, `uses: ./`, on GitHub's runners, with the paired release of `ghg` that rule 12 describes, and build a site from `test/fixtures/site/`, or are the scenarios of `features/`. Each scenario names the rule it checks with a tag, such as `@rule-7`, and runs a workflow that uses `./`, `./publish` or `./preview` through [act](https://github.com/nektos/act), on the machine itself, against stand-ins for GitHub on the loopback address: [WireMock](https://wiremock.org/) for its API, and `git http-backend` for the repository whose branch Pages serves. The releases of `ghg` stay on github.com. `npm run acceptance` runs them, and so does the job "the actions end to end", on every platform of the job "the action on each platform".

## Installing

1. The action always installs `ghg`, and puts its folder on the `PATH` of the job's later steps, so that a workflow can also run `ghg` itself, and its log says `ghg <version> is installed.` Checked by `test/services/installing.test.ts`, and by the job "the action on each platform", whose next step runs `ghg --version` and checks it prints the paired version. Also checked by the scenarios tagged `@rule-1` in `features/installing.feature`.
2. The input `ghg-version` names the release of `ghg` to install, such as `1.2.0`, or `v1.2.0` with the tag's `v`, a pre-release such as `1.3.0-rc.1` included, written as [Semantic Versioning](https://semver.org/) writes a version without build metadata. Anything that is not a version stops the action with `ghg-version must be a version of ghg, such as 1.2.0.` A workflow may name any release to install. To build, the action needs `ghg` 1.1.0 or newer, whose report it reads (rule 7): when it builds, a version older than that stops it before anything is downloaded, with `The action builds with ghg 1.1.0 or newer, not <version>.` One that names an older `ghg` without another option it uses is stopped by `ghg` itself, as gherkin-glass's rule 19 says. Checked by `test/policies/versions.test.ts` and `test/services/installing.test.ts`. Also checked by the scenarios tagged `@rule-2` in `features/installing.feature`.
3. When `ghg-version` is empty, its default, the action installs the newest stable release of `ghg` within its own major version, rule 11's: action v1 installs the newest `ghg` 1.x, never a 2.x. Only a published release whose tag is a plain version, such as `v1.2.0`, counts, never a draft or a pre-release. When none does, the action stops with `ghg has no release compatible with this action's version.` The releases are listed through GitHub's API with the input `token`, by default the workflow's own token, `github.token`, which is sent only when the workflow runs on github.com, since on GitHub Enterprise Server it is not a token of github.com. When they cannot be listed, the action stops with `The releases of ghg cannot be listed.` Checked by `test/policies/versions.test.ts`, `test/services/installing.test.ts`, `test/services/reading_inputs.test.ts` and `test/adapters/github_releases.test.ts`. It has no scenario, since the stand-in for GitHub's API does not list the releases of `ghg`, which stay on github.com.
4. The action installs the release's archive for the runner's system and processor, as gherkin-glass's rules 161 to 163 name it, `ghg-v<version>-<target>.tar.gz`, or `.zip` on Windows:

    | Runner | Target |
    | --- | --- |
    | Linux on x86-64 | `x86_64-unknown-linux-musl` |
    | Linux on ARM64 | `aarch64-unknown-linux-musl` |
    | macOS on Intel | `x86_64-apple-darwin` |
    | macOS on Apple silicon | `aarch64-apple-darwin` |
    | Windows on x86-64 | `x86_64-pc-windows-msvc` |
    | Windows on ARM64 | `aarch64-pc-windows-msvc` |

    On any other, it stops with `ghg has no build for <system> on <processor>.`, in the runner's own words for them, `RUNNER_OS` and `RUNNER_ARCH`, such as `ghg has no build for Linux on ARM.`, or `this system` and `this processor` when the runner does not say. An archive the release does not have stops it with `<archive> cannot be downloaded from the release v<version> of ghg.` Checked by `test/policies/targets.test.ts` and `test/services/installing.test.ts`, and by the job "the action on each platform" on `ubuntu-latest`, `ubuntu-24.04-arm`, `macos-26`, `macos-15-intel`, `windows-latest` and `windows-11-arm`. Also checked by the scenarios tagged `@rule-4` in `features/installing.feature`, which run on each platform.
5. The archive is checked against the release's `SHA256SUMS` file before anything is installed. An archive whose checksum differs stops the action with `<archive> does not match its checksum in SHA256SUMS.`, one the file does not list with `<archive> is not in the release's SHA256SUMS.`, a release without the file with `SHA256SUMS cannot be downloaded from the release v<version> of ghg.`, and an archive without `ghg`, or `ghg.exe` on Windows, at its root, with `<archive> has no ghg.` Checked by `test/policies/checksums.test.ts` and `test/services/installing.test.ts`.
6. An installed `ghg` is kept in the runner's tool cache, under `ghg/<version>/<processor>`, and a later run that finds it there installs it without downloading it again. GitHub's own runners start every job with an empty tool cache, so there it saves the download only when the action runs again in the same job; a self-hosted runner keeps it from job to job. Checked by `test/services/installing.test.ts`. Also checked by the scenarios tagged `@rule-6` in `features/installing.feature`.

## Building

7. The input `build` is `false` by default. When it is `true`, the action runs `ghg build` after installing it, in the workflow's workspace folder, with `--message-format=json`, so that `ghg` also prints how the build ended as one JSON object on its standard output, which the action reads (gherkin-glass's rule 231). When the build fails, its report in the log, the action stops with `ghg build stopped with status <status>.`, with the build's exit status. When the build passes but prints no such object, it stops with `ghg build gave no report of how it ended.` When the object's `outcome` is `nothing-to-build`, since the input holds no feature file, `ghg` writes nothing and says so in the log (gherkin-glass's rule 229), and the step passes. Any value but `true`, `false` or nothing stops the action with `build must be true or false.` Checked by `test/policies/build_arguments.test.ts`, `test/policies/build_report.test.ts`, `test/services/building.test.ts` and `test/adapters/exec_ghg_process.test.ts`, and by the job "the action on each platform", which checks the site was written. Also checked by the scenarios tagged `@rule-7` in `features/building.feature`.
8. Every option of `ghg build` that sets how a site is built, which is every option but `--help`, `--version` and `--message-format`, which the action gives itself (rule 7), has an input of the same name without its dashes: `config`, `input`, `output`, `title`, `version-name`, `front-page`, `only`, `preview` and `keep-in-output`. When `build` is `true`, each such input that is not empty is passed to `ghg build` as `--<name>=<value>`; an empty one, the default, is left out, so the configuration file and the defaults still apply. An option that takes no value, `--preview`, is passed as `--<name>` when its input is `true`, and left out when it is `false` or empty; any other value stops the action with `<name> must be true or false.` The one option that may be given more than once, `--keep-in-output`, takes one pattern on each line of its input, each passed as `--<name>=<value>` in the order of the lines; a line that is empty, or of white space only, is left out. Checked by `test/policies/build_arguments.test.ts`. Also checked by the scenarios tagged `@rule-8` in `features/building.feature`.
9. The inputs and the options of `ghg build` cannot drift apart. The job "the inputs against ghg build" installs the paired release of `ghg`, and fails when an option that `ghg build --help` lists has no input of the same name, other than `--message-format`, or an input other than `ghg-version`, `build` and `token` is not such an option. `test/policies/build_arguments.test.ts` fails when an input of `action.yml` is not passed to the build. Checked by those two.

## Annotations

10. When the action runs the build, each problem the build's JSON object lists under `errors` with a line, which its report also prints as `<path>:<line>: <message>`, as gherkin-glass's rules 16, 26, 187 to 190 and 231 write it, is also an error annotation on that file and line, with the message as its text, so that it shows on the pull request's changes. ghg names the configuration file and the front page's template by their paths from the workspace, and the action annotates them there. It names a file of the input folder by its path from that folder, so the action finds the folder as `ghg` does, and annotates the file in it: the input `input`; else the key `input` of the configuration file, the input `config` or `ghg.toml` in the workspace, relative to the folder of that file unless it is a whole path; else `features`, in that folder, or in the workspace when there is no configuration file. After the build, whether it passed or not, or after installing when `build` is not `true`, the action registers a problem matcher, `ghg`, so that a later step that runs `ghg build` itself has each such line annotated too, with its path as `ghg` printed it. Checked by `test/policies/report_annotations.test.ts`, `test/policies/report_paths.test.ts`, `test/policies/problem_matcher.test.ts`, `test/services/building.test.ts` and `test/services/running_action.test.ts`. Also checked by the scenarios tagged `@rule-10` in `features/annotations.feature`.

## Versions

11. The action shares only its major version with `ghg`, and has minor and patch numbers of its own. Its major version is that of the release of `ghg` it is paired with, which `paired-ghg.json` names; `package.json` gives the action's own version, of the same major version. Checked by `test/policies/versions.test.ts`, which reads both files.
12. The paired release is the one the action's checks install. A release of `ghg` that adds an option is followed by a pull request that pairs the action with it and adds the option's input, and then by a minor release of the action. Each week, `.github/workflows/weekly.yml` fails while the newest stable `ghg` of the action's major version is newer than the paired one, and runs the job "the action on each platform" with that newest `ghg`. Checked by the job "the paired ghg is the newest" of that workflow.

## Releases

A release is made by the release workflow, `.github/workflows/release.yml`, when a maintainer pushes a version's tag. Its scripts are in `.github/release/`.

13. Pushing a tag `v<version>` releases that version, and nothing else does. The tag is refused, and nothing is released, unless the version is the one `package.json` gives, the tagged commit is on `main`, and `CHANGELOG.md` has notes for the version, under the heading `## [<version>]`. Every reason a tag is refused is reported, not only the first. Checked by `.github/release/test-gate.sh`, with the changelogs of `test/fixtures/release/`.
14. A release is made only once every check of `.github/workflows/action.yml` passes on the tagged commit, `dist/` built again from it among them, which must not differ from the committed one. Checked by the release workflow, which runs them before it releases.
15. The notes of a release are the section of `CHANGELOG.md` for its version. That section is written before the tag, from what [git-cliff](https://git-cliff.org/) prints with the template in `cliff.toml`: the heading `## [<version>]`, then the changelog entries that the commits since the previous tag carry as trailers, under `### Added`, `### Changed`, `### Fixed` and `### Removed`, in that order and each only when it has entries, one list item per entry, oldest commit first. A commit whose subject does not follow [Conventional Commits](https://www.conventionalcommits.org/), such as a merge commit, adds nothing, nor does a trailer of any other kind, such as `Refs #N` or `Changelog: none`. Checked by `.github/release/test-notes.sh`, with the repository it makes.
16. The release workflow makes the GitHub release itself, titled with the tag and with the notes of rule 15. A version with a pre-release part, such as `1.1.0-rc.1`, is released as a pre-release, and only the newest version without one, among the repository's tags, is marked as its latest release. The release carries no files, since a workflow runs the action from the tagged commit. A version already released is left as it is, so that the workflow can be run again. Checked by `.github/release/test-publish.sh`, with a stand-in for `gh`.
17. A published version's tag, such as `v1.3.0`, never moves. When a release's tag is a version without a pre-release part, and no other tag of the repository is a newer such version of the same major version, the release workflow moves the tag of that major version, such as `v1`, to the released commit, once the GitHub release is made. So `uses: marlon-sousa/gherkin-glass-action@v1` runs the newest 1.x release of the action. A pre-release, a release before 1.0, and a release older than another of its major version move no tag. Checked by `.github/release/test-action-tag.sh`, with lists of tags it holds.

## Outputs

18. The action gives the job's later steps two outputs: `ghg-version`, the release of `ghg` it installed, such as `1.2.0`, and `site`, the folder the build wrote the site into, as the `output` of the build's JSON object gives it, relative to the workspace (gherkin-glass's rule 231), with `/` between folders on every system, such as `docs/site`. When the action does not build, or the build has nothing to build (rule 7), `site` is empty. Checked by `test/policies/build_report.test.ts` and `test/services/running_action.test.ts`. Also checked by the scenarios tagged `@rule-18` in `features/outputs.feature`.

## Publishing

Two more actions, in folders of this repository beside the root action, publish the site where it is served, as issue [#9](https://github.com/marlon-sousa/gherkin-glass-action/issues/9) decided, shaped as actions/cache keeps `restore` and `save` beside its own: `uses: marlon-sousa/gherkin-glass-action/publish@v1` adds a version of the site, and `uses: marlon-sousa/gherkin-glass-action/preview@v1` publishes a pull request's preview and removes it when the pull request closes. They share the root action's tags and releases (rules 13 to 17). GitHub lists only the root action on the Marketplace, so its README links them. Publishing is optional: a project that publishes its own site uses neither, or only `preview`, writing its own site into the same branch and leaving `previews/` there alone.

19. `publish` and `preview` share these inputs. `to`, `github-pages` by default, says where the site is published; it is the only value today, and any other stops the action with `to must be github-pages.` `branch`, `gh-pages` by default, names the branch Pages serves; empty, it stops the action with `branch must name a branch.` `folder`, empty by default, names the folder of that branch the site goes into, such as `features`, written with `/` and relative to the branch's root; empty, the site goes into the branch's root. A `folder` that is a whole path, or has an empty, `.` or `..` folder in it, stops the action with `folder must be a folder of branch, such as features.` `ghg-version` and `token` are the root action's: each action installs `ghg` as rules 1 to 6 say, and `token`, the workflow's own by default, also reads how Pages is set and pushes, on the workflow's own server, `GITHUB_SERVER_URL` and `GITHUB_API_URL`. `config`, `input`, `title`, `front-page` and `keep-in-output` are passed to `ghg build` as rule 8 says, with what the action adds, and `preview` adds to the title, as rule 30 says, and its report is read as rule 7 says and annotated as rule 10 says. The action keeps the files Pages reads at the root of the output folder, `.nojekyll` and `CNAME`, by passing `--keep-in-output=/.nojekyll` and `--keep-in-output=/CNAME` first (gherkin-glass's rules 224 to 227). The patterns of `keep-in-output` follow those two; when it is empty, the patterns of the configuration file's `keep_in_output` do, since `ghg` reads the key only when the command line gives no pattern. A pattern of the key that is not valid in the gitignore syntax is then a mistake on the command line, which stops the build without a report, with its status (gherkin-glass's rules 19 and 226). Each action gives the address of what it published as the output `address`. Checked by `test/policies/site_inputs.test.ts`, `test/policies/kept_in_output.test.ts`, `test/services/reading_site_inputs.test.ts`, `test/services/publishing_version.test.ts`, `test/services/publishing_preview.test.ts` and `test/services/running_site_actions.test.ts`, and by the job "the publish and preview actions stopping", which runs both actions, `uses: ./publish` and `uses: ./preview`, until they stop at an input they cannot use. Also checked by the scenarios tagged `@rule-19` in `features/publishing.feature` and `features/publish_action.feature`.
20. Before it builds anything, each action reads how Pages is set, through GitHub's API, which needs the workflow's permission `pages: read`. Pages must deploy from a branch, `branch`, and serve the branch's root, or a folder that holds `folder`, such as `/docs` for a `folder` of `docs/features`. When Pages is not set so, and the branch exists, the action stops with `Pages does not deploy from the branch <branch>: in the repository's Settings, under Pages, set the source to "Deploy from a branch" and choose <branch>.` When the branch does not exist, the action first makes it, with one empty commit, pushed with `token`, and then stops with `The branch <branch> is made: in the repository's Settings, under Pages, set the source to "Deploy from a branch" and choose <branch>, and add an empty .nojekyll file at its root.`, since Pages can be set only to a branch that exists; when that push is refused, it stops with rule 22's `The site cannot be pushed to <branch>: the workflow needs the permission contents: write.` When Pages serves a folder that does not hold `folder`, it stops with `Pages serves the folder <folder> of <branch>, so folder must be in it.` When the settings cannot be read, for another reason than Pages being off, it stops with `The settings of Pages cannot be read: the workflow needs the permission pages: read.` Checked by `test/policies/pages_source.test.ts`, `test/services/publishing.test.ts`, `test/adapters/github_repository_api.test.ts` and `test/adapters/git_site_branch.test.ts`. Also checked by the scenarios tagged `@rule-20` in `features/publishing.feature`.
21. Pages runs Jekyll on a branch unless a `.nojekyll` file sits at the root of the folder it serves, and Jekyll leaves out every file whose name starts with `_`, such as the page of `_draft.feature`. The actions never write `.nojekyll`: the site's maintainer adds it once. When it is missing, the action stops before it changes the branch, with `Pages runs Jekyll on <branch>, which leaves out pages whose names start with _: add an empty .nojekyll file to the folder <folder> of <branch>.`, where the folder is the one Pages serves, such as `/` or `/docs`. `ghg` refuses an output folder that holds a file it did not write (gherkin-glass's rule 38), but leaves alone what the action keeps (rule 19), so the site may go into the folder that holds `.nojekyll`, the branch's root among them. Checked by `test/policies/pages_source.test.ts` and `test/services/publishing.test.ts`. Also checked by the scenarios tagged `@rule-21` in `features/publishing.feature`.
22. The action fetches the branch's newest commit, builds into it or removes from it, and commits what changed, as `github-actions[bot]`, then pushes it with `token`, which needs the workflow's permission `contents: write`. When nothing changed, such as when the site built is the one already published, it makes no commit, pushes nothing, and its log says `The site on <branch> is already up to date.` When another push reached the branch first, it starts again from the branch's newest commit, three times in all, and then stops with `The site cannot be pushed to <branch>.` When the push is refused for another reason, most often a token without that permission, it stops with `The site cannot be pushed to <branch>: the workflow needs the permission contents: write.`, and its log gives git's own message. Checked by `test/services/publishing.test.ts` and `test/adapters/git_site_branch.test.ts`, against a repository on disk. Also checked by the scenarios tagged `@rule-22` in `features/publishing.feature` and `features/publish_action.feature`.

## The publish action

23. `publish` adds a version of the site to `folder`, on any event, as a versioned build, as gherkin-glass's rule 120 describes, which ghg adds beside the versions already there, under its versions page. A missing or empty `folder` is made and marked as ghg's; versions already there stay, and a version of the same name is replaced; a `folder` that holds anything ghg did not write is refused, writing and deleting nothing; and the branch outside `folder`, such as a site's own `index.html`, is never touched (gherkin-glass's rules 38, 122 and 123). The version is named by the input `version-name` when it is not empty, else by the tag or branch that ran, `GITHUB_REF_NAME`, with every `/` in it made a `-`, such as `feature-login` for `feature/login`, since a version name is one folder name (gherkin-glass's rule 121). The commit's message is `Publish the site's version <name>`. When `ghg` has nothing to build (rule 7), the action commits nothing, its log says `ghg read no feature file, so nothing is published.`, and `address` is empty. Once pushed, its log says `The site is published on <branch>, at <address>.`, where the address is that of the version's folder on the site Pages names, which is also the output `address`. Checked by `test/policies/workflow_event.test.ts`, `test/services/publishing_version.test.ts` and `test/services/running_site_actions.test.ts`. Also checked by the scenarios tagged `@rule-23` in `features/publish_action.feature`.

## The preview action

24. `preview` acts on a `pull_request` event only. On any other event, it stops the action with `preview acts on a pull request, not on <event>.`, with the event's name, such as `push`. Checked by `test/policies/workflow_event.test.ts` and `test/services/running_site_actions.test.ts`. Also checked by the scenarios tagged `@rule-24` in `features/preview_action.feature`.
25. On a pull request whose head branch is in another repository, a fork, the workflow's token cannot push, so the action publishes nothing: its log says, as a notice, `This pull request comes from a fork, whose token cannot push, so its preview is not published.` It installs nothing, and the step passes. Checked by `test/policies/workflow_event.test.ts` and `test/services/running_site_actions.test.ts`. Also checked by the scenarios tagged `@rule-25` in `features/preview_action.feature`.
26. On a pull request, unless it is closed, the action builds a preview, as gherkin-glass's rule 211 describes, into `previews/pr-<number>` of `folder`, where ghg leaves it alone beside the versions (gherkin-glass's rules 122 and 213), and commits it with the message `Publish the preview of pull request #<number>`. Once pushed, its log says `The site is published on <branch>, at <address>.`, the address of the preview's folder, which is also the output `address`. When `ghg` has nothing to build (rule 7), such as when the pull request removes the last feature file, or with `changed-only`, when the files it changes in the input folder are none of them feature files, the action leaves an earlier preview and its comment as they are, as rule 28 does, and its log says `ghg read no feature file, so no preview is published.` When the pull request is closed, merged or not, the action installs and builds nothing, removes that folder instead, with the message `Remove the preview of pull request #<number>`, and its log says `The preview of pull request #<number> is removed from <branch>.`; when the folder is not there, there is nothing to remove. The workflow lists `closed` among the pull request's types for it. Checked by `test/policies/workflow_event.test.ts` and `test/services/publishing_preview.test.ts`. Also checked by the scenarios tagged `@rule-26` in `features/preview_action.feature`.
27. Once a preview is pushed, the action writes its address on the pull request in one comment, `The preview of this pull request's feature files is at <address>.`, which it edits on every later push rather than adding another. It finds its comment by the line `<!-- gherkin-glass-action preview -->` at the comment's start, which a second line, `<!-- built from <commit> -->`, follows, naming the commit of the pull request's head the preview was built from, as rule 29 uses it; neither shows on the pull request. Once a closed pull request's preview is removed, it edits that comment, when there is one, to say `The preview of this pull request was removed when it closed.` Writing the comment needs the workflow's permission `pull-requests: write`; when it cannot be written, the action stops with `The comment of the pull request's preview cannot be written.` Checked by `test/policies/preview_comment.test.ts`, `test/services/publishing_preview.test.ts` and `test/adapters/github_repository_api.test.ts`. Also checked by the scenarios tagged `@rule-27` in `features/preview_action.feature`.
28. The input `changed-only`, `false` by default, makes a preview show only the feature files the pull request changes; any value but `true`, `false` or nothing stops the action with `changed-only must be true or false.` The action lists the files the pull request changes through GitHub's API, the first 3000, which is the most GitHub lists, leaves out the files it removes, and keeps those inside the input folder, found as rule 10 finds it, with their paths from the repository's root, which is the workspace. When none is kept, the action publishes nothing, leaves an earlier preview as it is, and its log says `This pull request changes no file of the input folder, so no preview is published.` Otherwise it gives ghg the kept files with `--only`, written one a line in a file of the runner's temporary folder, and ghg tells which of them are feature files it reads (gherkin-glass's rules 204 to 208). When the files cannot be listed, the action stops with `The files the pull request changes cannot be listed.` When a pull request closes, `changed-only` changes nothing. Checked by the job "the publish and preview actions stopping", and by `test/policies/site_inputs.test.ts`, `test/policies/changed_files.test.ts`, `test/services/publishing_preview.test.ts` and `test/adapters/github_repository_api.test.ts`. Also checked by the scenarios tagged `@rule-28` in `features/preview_action.feature`.
29. A preview whose sources have not changed since it was built is not built again, since it would be the same. Before it builds, the action compares the commit its comment names (rule 27) with the commit of the pull request's head, through GitHub's API, and when none of the files the commits between them change, the files they remove and the previous paths of those they move included, is inside the input folder, or is the configuration file or the front page's Markdown file, it leaves the preview as it is, edits its comment to name the head, and its log says `The commits since the preview was built change no file it is built from, so the preview is left as it is.` A change to the workflow alone, such as to an input, does not count, nor does a change to the pull request's base branch, which the workspace's checkout merges in. It builds all the same when the comment names no commit, when the preview is not on the branch, its marker `ghg-site.json` missing, or when the commits cannot be compared: when the head does not follow the commit named, such as after a force push, or when GitHub's comparison lists 300 files, the most it gives, and so may leave some out. A run that fails or is cancelled leaves the comment as it was, so the next run compares from the last preview pushed. Checked by `test/policies/changed_files.test.ts`, `test/policies/preview_comment.test.ts`, `test/policies/workflow_event.test.ts`, `test/services/publishing_preview.test.ts` and `test/adapters/github_repository_api.test.ts`. Also checked by the scenarios tagged `@rule-29` in `features/preview_action.feature`.
30. A preview's title names its pull request, so that it is told from the site's versions at a glance ([#19](https://github.com/marlon-sousa/gherkin-glass-action/issues/19), decision 8). The action passes `--title` with the site's title as `ghg` would give it, then a comma, a space and `pull request #<number>`, such as `Shop, pull request #12`. The site's title is the input `title`; else the key `title` of the configuration file, the input `config` or `ghg.toml` in the workspace; else `Feature files`, `ghg`'s own (gherkin-glass's rule 81). A workflow needs no configuration file: when there is none, when it is not valid TOML, or when its `title` is not text or is empty, the action uses the input or `Feature files`, and `ghg` reports what is wrong with the file itself (gherkin-glass's rule 26). So a preview's site always has a title, and `ghg`'s hint about a site without one (gherkin-glass's rule 17) is not given. A front page's template gives the front page its own `h1` and title (gherkin-glass's rule 187), so only the other pages name the pull request there. `publish` passes `title` as it is, as rule 8 says. Checked by `test/policies/preview_title.test.ts`, `test/services/publishing_preview.test.ts` and `test/services/publishing_version.test.ts`. Also checked by the scenarios tagged `@rule-30` in `features/preview_action.feature`.
