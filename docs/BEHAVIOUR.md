# Behaviour

What gherkin-glass-action promises, in terms a test can observe. Each section is written when its issue is agreed, before it is built, and every rule in it names the test that checks it ([AGENTS.md](../AGENTS.md), "Rules", rule 2). What `ghg` itself does is promised by gherkin-glass's [docs/BEHAVIOUR.md](https://github.com/marlon-sousa/gherkin-glass/blob/main/docs/BEHAVIOUR.md), whose rules this document names as "gherkin-glass's rule N".

## Status

Agreed so far:

- Every section below, issue [#1](https://github.com/marlon-sousa/gherkin-glass-action/issues/1), which carries over gherkin-glass's rules 169 to 177, of its own action, as that issue's decisions change them.

## The action

A step of a GitHub Actions workflow that says `uses: marlon-sousa/gherkin-glass-action@v1` installs `ghg` on the runner and, when asked, builds a site with it. The action is a JavaScript action, `using: node24` in `action.yml`, which the runner runs on the Node it carries itself, so it needs no Node on the job's `PATH`, and runs alike on GitHub's own runners and on self-hosted ones.

When the action stops, it says why in one sentence, which the workflow's log shows as an error, and the step fails. Every input is checked before anything is listed or downloaded. An error the action does not foresee, which is a bug, stops it with `The action failed unexpectedly: <error>`. Checked by `test/services/running_action.test.ts` and `test/services/reading_inputs.test.ts`.

The tests named below are under `test/`, run by `npm test`, unless they are jobs of `.github/workflows/action.yml`, which run the action itself, `uses: ./`, on GitHub's runners, with the paired release of `ghg` that rule 12 describes, and build a site from `test/fixtures/site/`.

## Installing

1. The action always installs `ghg`, and puts its folder on the `PATH` of the job's later steps, so that a workflow can also run `ghg` itself, and its log says `ghg <version> is installed.` Checked by `test/services/installing.test.ts`, and by the job "the action on each platform", whose next step runs `ghg --version` and checks it prints the paired version.
2. The input `ghg-version` names the release of `ghg` to install, such as `1.2.0`, or `v1.2.0` with the tag's `v`, a pre-release such as `1.3.0-rc.1` included, written as [Semantic Versioning](https://semver.org/) writes a version without build metadata. Anything that is not a version stops the action with `ghg-version must be a version of ghg, such as 1.2.0.` A workflow may name any release; one that names an older `ghg` without an option it uses is stopped by `ghg` itself, as gherkin-glass's rule 19 says. Checked by `test/policies/versions.test.ts`.
3. When `ghg-version` is empty, its default, the action installs the newest stable release of `ghg` within its own major version, rule 11's: action v1 installs the newest `ghg` 1.x, never a 2.x. Only a published release whose tag is a plain version, such as `v1.2.0`, counts, never a draft or a pre-release. When none does, the action stops with `ghg has no release compatible with this action's version.` The releases are listed through GitHub's API with the input `token`, by default the workflow's own token, `github.token`, which is sent only when the workflow runs on github.com, since on GitHub Enterprise Server it is not a token of github.com. When they cannot be listed, the action stops with `The releases of ghg cannot be listed.` Checked by `test/policies/versions.test.ts`, `test/services/installing.test.ts`, `test/services/reading_inputs.test.ts` and `test/adapters/github_releases.test.ts`.
4. The action installs the release's archive for the runner's system and processor, as gherkin-glass's rules 161 to 163 name it, `ghg-v<version>-<target>.tar.gz`, or `.zip` on Windows:

    | Runner | Target |
    | --- | --- |
    | Linux on x86-64 | `x86_64-unknown-linux-musl` |
    | Linux on ARM64 | `aarch64-unknown-linux-musl` |
    | macOS on Intel | `x86_64-apple-darwin` |
    | macOS on Apple silicon | `aarch64-apple-darwin` |
    | Windows on x86-64 | `x86_64-pc-windows-msvc` |

    On any other, it stops with `ghg has no build for <system> on <processor>.`, in the runner's own words for them, `RUNNER_OS` and `RUNNER_ARCH`, such as `ghg has no build for Windows on ARM64.`, or `this system` and `this processor` when the runner does not say. An archive the release does not have stops it with `<archive> cannot be downloaded from the release v<version> of ghg.` Checked by `test/policies/targets.test.ts` and `test/services/installing.test.ts`, by the job "the action on each platform" on `ubuntu-latest`, `ubuntu-24.04-arm`, `macos-latest`, `macos-15-intel` and `windows-latest`, and by the job "the action on a platform without a build" on `windows-11-arm`.
5. The archive is checked against the release's `SHA256SUMS` file before anything is installed. An archive whose checksum differs stops the action with `<archive> does not match its checksum in SHA256SUMS.`, one the file does not list with `<archive> is not in the release's SHA256SUMS.`, a release without the file with `SHA256SUMS cannot be downloaded from the release v<version> of ghg.`, and an archive without `ghg`, or `ghg.exe` on Windows, at its root, with `<archive> has no ghg.` Checked by `test/policies/checksums.test.ts` and `test/services/installing.test.ts`.
6. An installed `ghg` is kept in the runner's tool cache, under `ghg/<version>/<processor>`, and a later run that finds it there installs it without downloading it again. GitHub's own runners start every job with an empty tool cache, so there it saves the download only when the action runs again in the same job; a self-hosted runner keeps it from job to job. Checked by `test/services/installing.test.ts`.

## Building

7. The input `build` is `false` by default. When it is `true`, the action runs `ghg build` after installing it, in the workflow's workspace folder, and when the build fails, its report in the log, the action stops with `ghg build stopped with status <status>.`, with the build's exit status. Any value but `true`, `false` or nothing stops the action with `build must be true or false.` Checked by `test/policies/build_arguments.test.ts` and `test/services/building.test.ts`, and by the job "the action on each platform", which checks the site was written.
8. Every option of `ghg build` that sets how a site is built, which is every option but `--help` and `--version`, has an input of the same name without its dashes: `config`, `input`, `output`, `title`, `version-name`, `front-page`, `only` and `preview`. When `build` is `true`, each such input that is not empty is passed to `ghg build` as `--<name>=<value>`; an empty one, the default, is left out, so the configuration file and the defaults still apply. An option that takes no value, `--preview`, is passed as `--<name>` when its input is `true`, and left out when it is `false` or empty; any other value stops the action with `<name> must be true or false.` Checked by `test/policies/build_arguments.test.ts`.
9. The inputs and the options of `ghg build` cannot drift apart. The job "the inputs against ghg build" installs the paired release of `ghg`, and fails when an option that `ghg build --help` lists has no input of the same name, or an input other than `ghg-version`, `build` and `token` is not such an option. `test/policies/build_arguments.test.ts` fails when an input of `action.yml` is not passed to the build. Checked by those two.

## Annotations

10. When the action runs the build, each line of the build's report that names a file and a line, `<path>:<line>: <message>`, as gherkin-glass's rules 16, 26 and 187 to 190 write it, is also an error annotation on that file and line, with the message as its text, so that it shows on the pull request's changes. ghg names the configuration file and the front page's template by their paths from the workspace, and the action annotates them there. It names a file of the input folder by its path from that folder, so the action finds the folder as `ghg` does, and annotates the file in it: the input `input`; else the key `input` of the configuration file, the input `config` or `ghg.toml` in the workspace, relative to the folder of that file unless it is a whole path; else `features`, in that folder, or in the workspace when there is no configuration file. After the build, whether it passed or not, or after installing when `build` is not `true`, the action registers a problem matcher, `ghg`, so that a later step that runs `ghg build` itself has each such line annotated too, with its path as `ghg` printed it. Checked by `test/policies/report_annotations.test.ts`, `test/policies/report_paths.test.ts`, `test/policies/problem_matcher.test.ts`, `test/services/building.test.ts`, `test/services/running_action.test.ts` and `test/adapters/exec_ghg_process.test.ts`.

## Versions

11. The action shares only its major version with `ghg`, and has minor and patch numbers of its own. Its major version is that of the release of `ghg` it is paired with, which `paired-ghg.json` names; `package.json` gives the action's own version, of the same major version. Checked by `test/policies/versions.test.ts`, which reads both files.
12. The paired release is the one the action's checks install. A release of `ghg` that adds an option is followed by a pull request that pairs the action with it and adds the option's input, and then by a minor release of the action. Each week, `.github/workflows/weekly.yml` fails while the newest stable `ghg` of the action's major version is newer than the paired one, and runs the job "the action on each platform" with that newest `ghg`. Checked by the job "the paired ghg is the newest" of that workflow.

## Releases

A release is made by the release workflow, `.github/workflows/release.yml`, when a maintainer pushes a version's tag. Its scripts are in `.github/release/`.

13. Pushing a tag `v<version>` releases that version, and nothing else does. The tag is refused, and nothing is released, unless the version is the one `package.json` gives, the tagged commit is on `main`, and `CHANGELOG.md` has notes for the version, under the heading `## [<version>]`. Every reason a tag is refused is reported, not only the first. Checked by `.github/release/test-gate.sh`, with the changelogs of `test/fixtures/release/`.
14. A release is made only once every check of `.github/workflows/action.yml` passes on the tagged commit, `dist/` built again from it among them, which must not differ from the committed one. Checked by the release workflow, which runs them before it releases.
15. The notes of a release are the section of `CHANGELOG.md` for its version. That section is written before the tag, from what [git-cliff](https://git-cliff.org/) prints with the template in `cliff.toml`: the heading `## [<version>]`, then the changelog entries that the commits since the previous tag carry as trailers, under `### Added`, `### Changed`, `### Fixed` and `### Removed`, in that order and each only when it has entries, one list item per entry, oldest commit first. A commit whose subject does not follow [Conventional Commits](https://www.conventionalcommits.org/), such as a merge commit, adds nothing, nor does a trailer of any other kind, such as `Refs #N` or `Changelog: none`. Checked by `.github/release/test-notes.sh`, with the repository it makes.
16. A version with a pre-release part, such as `1.1.0-rc.1`, is released on GitHub as a pre-release. Checked by the tests of the `create-release` action of [itinera-dev/actions](https://github.com/itinera-dev/actions), which makes the release.
17. A published version's tag, such as `v1.3.0`, never moves. When a release's tag is a version without a pre-release part, and no other tag of the repository is a newer such version of the same major version, the release workflow moves the tag of that major version, such as `v1`, to the released commit, once the GitHub release is made. So `uses: marlon-sousa/gherkin-glass-action@v1` runs the newest 1.x release of the action. A pre-release, a release before 1.0, and a release older than another of its major version move no tag. Checked by `.github/release/test-action-tag.sh`, with lists of tags it holds.
